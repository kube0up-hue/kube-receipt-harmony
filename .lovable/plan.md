# خطة بناء نظام KUBE Supplier Receiving

نظام داخلي عربي RTL لتسجيل طلبات واستلامات الموردين ومطابقتها مع الفواتير الأسبوعية.

## نطاق المرحلة الأولى (MVP قابل للاستخدام فعليًا)

سأبني النظام على مراحل داخل نفس المشروع. المرحلة الأولى تغطي المسار الأساسي كاملًا، ثم نتوسع في المراحل التالية بناءً على أولوياتك.

### المرحلة 1 — الأساس + واجهة موظف الفرع (هذه الخطة)
1. تفعيل Lovable Cloud (Supabase) + إعداد التخزين للصور.
2. قاعدة البيانات الكاملة (كل الجداول التي يحتاجها النظام لاحقًا).
3. نظام الأدوار: `branch_employee` / `accountant` / `admin` مع RLS.
4. تسجيل دخول الموظف بـ PIN (بدون بريد) + تسجيل دخول المحاسب/الإدارة بالبريد.
5. واجهة الموظف (Mobile-first, RTL):
   - تسجيل طلب جديد (اختيار مورد + منتجات + كميات + تاريخ توصيل متوقع + ملاحظة).
   - قائمة "بانتظار الاستلام".
   - شاشة استلام الطلب مع كل الحسابات التلقائية (مقبول/فرق/حالة)، رفع صور، ملاحظات إلزامية عند الفرق، زر "تعبئة المستلم مثل المطلوب"، شاشة تأكيد بالإجماليات.
   - "استلامات اليوم" + "سجل آخر 7 أيام".
   - زر "لا يوجد استلام اليوم" (سجل بدون إغلاق طلبات مفتوحة).
6. بيانات أولية: الموردان الافتراضيان والمنتجات المذكورة.
7. تصميم KUBE: أبيض/أسود + أحمر KUBE للتنبيهات، أزرار كبيرة، بطاقات للمنتجات على الجوال.

### المرحلة 2 — واجهة المحاسب والمطابقة
- إنشاء فاتورة مورد + رفع ملف/صورة.
- تجميع تلقائي للاستلامات ضمن الفترة (حسب تاريخ الاستلام الفعلي، لكل مورد على حدة).
- جدول المطابقة بكل الحالات المطلوبة.
- منع تحويل فاتورة غير مطابقة إلى "جاهزة للسداد" إلا بموافقة إدارة + سبب.

### المرحلة 3 — لوحة الإدارة
- اعتماد/رفض الاستلامات، إعادة سجل للمراجعة، اعتماد الفواتير.
- تسجيل السداد بكل حقوله + صورة التحويل.
- إدارة الموظفين/الموردين/المنتجات (إخفاء، ترتيب، منع حذف المرتبط بعمليات).

### المرحلة 4 — التقارير والإحصائيات
- بطاقات الإحصائيات المطلوبة.
- التقارير بكل الفلاتر + تصدير PDF / Excel / CSV / طباعة.
- سجل النشاط الكامل (activity log) لكل عملية.

## تفاصيل تقنية

**قاعدة البيانات (جداول رئيسية):**
```
suppliers, products, units(enum), employees (PIN hash),
user_roles, orders, order_items,
receipts, receipt_items, receipt_photos,
invoices, invoice_items, invoice_matches,
payments, activity_log
```

**PIN Auth للموظف:** جدول `employees` يحفظ `pin_hash` (bcrypt عبر Edge Function/server function). تسجيل الدخول ينشئ جلسة Supabase مخصصة عبر server function موقّعة، ثم يُستخدم `has_role()` في RLS.

**RLS:**
- الموظف: يرى/يضيف طلباته واستلامات فرعه فقط، لا يرى `invoices` أو الأسعار.
- المحاسب: قراءة الاستلامات + كتابة الفواتير والمطابقات، لا يعدّل استلام معتمد.
- الإدارة: كل شيء.

**الحسابات:** تُحسب الحقول المشتقة (مقبول/فرق/الحالة) داخل التطبيق للعرض، مع Constraints في DB لمنع القيم السالبة و Trigger لتثبيت الحالة عند الحفظ.

**التخزين:** Bucket خاص للصور (`receipt-photos`, `invoice-files`, `payment-proofs`) مع RLS.

**RTL/تصميم:** `dir="rtl"`, خط عربي (Cairo/IBM Plex Sans Arabic)، design tokens في `styles.css` (أبيض/أسود + `--kube-red`)، بدون ألوان hardcoded.

## سؤال قبل البدء
سأبدأ فورًا بالمرحلة 1 (الأساس + واجهة الموظف كاملة). المراحل 2-4 أنفذها بالتتابع في رسائل لاحقة لتفادي كتلة ضخمة واحدة صعبة المراجعة. إذا تريد ترتيبًا مختلفًا (مثلًا: كل الـ backend + كل الواجهات دفعة واحدة) أخبرني.
