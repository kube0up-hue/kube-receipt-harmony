# KUBE Supplier Receiving — ملخص المنصة وأساس التطوير

## ١. الفكرة الأساسية

**KUBE Supplier Receiving** هو نظام داخلي عربي (RTL) لتسجيل طلبات الموردين ومتابعة استلامها ومطابقة فواتيرهم بالكميات الفعلية. الهدف: إغلاق الحلقة بين "طلب المنتج" و"دفع المورد"، بحيث لا تُسدّد فاتورة إلا بعد التحقق من الاستلام الفعلي والأسعار المتفق عليها.

## ٢. الجهات المستهدفة داخل المؤسسة

| الدور | المستخدم | ما يفعله |
|------|----------|----------|
| **موظف الفرع** | يعمل من الجوال/الكمبيوتر | يسجيل الطلب اليومي من المورد، ثم يستلم المنتجات ويصور كل صنف، ويسجل الكميات المقبولة والتالفة والنقص. |
| **المحاسب** | يعمل من الكمبيوتر | يطابق فواتير الموردين مع استلامات الفترة، يحدد المستحق للسداد، ويتابع تقرير المبالغ المستحقة. |
| **المدير/المسؤول** | لوحة الإدارة | يدير الموردين والمنتجات والأسعار والموظفين والصلاحيات، ويراجع التقارير وفحص سلامة البيانات. |

## ٣. دورة العمل الرئيسية

```text
[موظف الفرع] ── تسجيل طلب ──► [قاعدة البيانات]
       │
       ▼
[موظف الفرع] ── استلام + صور + كميات ──► [قاعدة البيانات]
       │
       ▼ (إشعار تلقائي إلى Telegram)
[المحاسب] ── مطابقة فاتورة بالاستلامات ──► [فاتورة + بنود + سجل مطابقة]
       │
       ▼
[المدير] ── اعتماد/سداد ──► [تسجيل دفعة + إغلاق الفاتورة]
```

### ٣.١ تسجيل الطلب
- الموظف يختار المورد والمنتجات والكميات المطلوبة.
- النظام يولّد رقم طلب فريد (مثل ORD-1001).
- الطلب يدخل بحالة "بانتظار الاستلام".

### ٣.٢ الاستلام
- عند وصول البضاعة، الموظف يفتح الطلب ويسجّل:
  - الكمية المستلمة لكل صنف.
  - الكمية التالفة.
  - الكمية المقبولة (تُحسب تلقائياً).
  - صورة إلزامية **لكل صنف**.
- بعد الحفظ، الطلب لا يظهر مرة أخرى في قائمة "بانتظار الاستلام".
- يُرسل إشعار Telegram فوري يحتوي: المورد، رقم الاستلام، التاريخ/الوقت، المستلم، الأصناف، النقص، التالف، الملخص.

### ٣.٣ مطابقة الفاتورة
- المحاسب يختار المورد وتاريخي بداية/نهاية الفترة.
- النظام يجمع كل استلامات تلك الفترة تلقائياً.
- يظهر لكل صنف: المطلوب، المستلم، المقبول، التالف، الكمية بالفاتورة، سعر الوحدة، المستحق للسداد، فرق المبلغ.
- يُمنع الحفظ إذا كان هناك أصناف بدون سعر (مع إمكانية تأكيد استثناء).
- تُحذّر المنصة إذا كانت فترة الفاتورة تتقاطع مع فاتورة سابقة لنفس المورد.
- حفظ الفاتورة والمطابقة يتم في **عملية قاعدة بيانات واحدة** (ذرية) عبر `submit_invoice_match`.

### ٣.٤ السداد
- تقرير "المبالغ المستحقة للسداد" يعرض كل فاتورة مع حالتها والمدفوع والمتبقي.
- المدير يسجّل الدفعة ويرفع إثبات التحويل.

## ٤. الأدوار والصلاحيات

النظام يستخدم ثلاثة أدوار رئيسية:
- `admin` — المدير، يملك كل شيء.
- `accountant` — المحاسب، يطابق الفواتير ويتابع المستحقات.
- `branch_employee` — موظف الفرع، يسجّل الطلبات والاستلامات.

بالإضافة إلى الأدوار، يوجد نظام صلاحيات دقيق (`user_permissions`) يتيح للمدير تفعيل/تعطيل صلاحيات محددة لكل مستخدم، مثل:
- إنشاء فاتورة ومطابقتها.
- تعديل أسعار المنتجات.
- حذف الموردين أو المنتجات.
- عرض صور الاستلام.
- التقارير والتصدير.

| `/admin/orders` | الطلبات والاستلامات | مراجعة كل الطلبات والاستلامات. |

## ٦. الأسس التقنية

- **الإطار:** TanStack Start (React 19 + Vite 7) مع توجيه مبني على الملفات (`src/routes`).
- **الخلفية والمصادقة:** Lovable Cloud (Supabase) — Auth + Postgres + Storage.
- **الاستعلامات:** TanStack Query مع Realtime لتحديث اللحظي.
- **التصميم:** Tailwind CSS v4 + shadcn/ui، اتجاه RTL، هوية KUBE (أبيض/أسود/أحمر للتنبيهات).
- **التواصل:** Telegram Gateway لإشعارات الاستلام.
- **التصدير:** CSV/Excel/PDF للتقارير والمطابقات.

## ٨. مبادئ التطوير التي لا يجب المساس بها

1. **الوقت الزمني:** كل التواريخ والفترات تُحسب بتوقيت **الرياض (Asia/Riyadh)**، لا UTC.
2. **الذرية:** حفظ الطلب، حفظ الاستلام، وحفظ الفاتورة كلها عمليات ذرية عبر RPCs.
3. **الأمان:** RLS مفعل على كل الجداول، والدوال الحساسة SECURITY DEFINER محصورة في `service_role`.
4. **الصور:** كل صنف مستلم يجب أن يكون له صورة؛ الصور مقيدة بصلاحيات صارمة.
5. **الأسعار:** لا يُسمح بحفظ صنف جديد بسعر صفر دون تأكيد صريح؛ المستحق = الكمية المقبولة × سعر الوحدة.
6. **منع التكرار:** لا يُحسب نفس الاستلام مرتين؛ الفواتير المتقاطعة تُحذّر وتُمنع افتراضياً.
7. **الإشعارات:** Telegram يُرسل فور اعتماد الاستلام، مع تتبع الحالة (sent/pending/failed) وإعادة إرسال يدوية للمدير.
8. **الصلاحيات:** كل ميزة جديدة يجب أن تُربط بصلاحية من `src/lib/permissions.ts` وتُحمى بـ `PermissionGuard` أو `Can`.

## ٩. حالة التطوير الحالية والتركيز القادم

- مسار الطلب والاستلام مستقر بنيوياً.
- مطابقة الفواتير تعمل بحسابات مالية دقيقة (خانتان عشريتان).
- نظام الصلاحيات جاهز وقابل للتوسع.
- التركيز الحالي: ضبط الأسعار الناقصة، منع تداخل فترات الفواتير، تحسين تجربة المعاينة الجوّال/كمبيوتر، وتطوير التقارير والتصدير.
